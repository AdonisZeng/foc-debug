# 排查卡：故障处理与状态机事务类坑（诊断码仲裁 · 恢复放行 · 开波授权 · 重启计时）

> 定位：保护**判据本身正确、硬件也正常**，但"报出来的原因不对"、"故障后行为与
> 设计不符"、"重启节奏被莫名改变"时查这张卡。特征是：
> 1) 现场读到的故障码/子类码与真实物理原因对不上；
> 2) 故障停机后电机又动起来，或该锁死的没锁死、该自恢复的没恢复；
> 3) 重启间隔看起来"忽长忽短"。
> 这类问题的根因不在阈值与判据，而在**故障状态是多方共享的全局量，且写入发生在
> 多个中断优先级里**——排查时按"谁在什么时刻写了哪些共享字节"来推演，而不是
> 反复调阈值。
> 条目来自 25W 平台保护链重构（代码审查 + 严格推导，见 `motor-profiles/diman-25w-fan-motor.md`）。

## 坑1：诊断码被后续低优先级事件覆盖，现场读到的"故障原因"不是真实原因

**适用标签**：`多中断源` `诊断码` `故障记录` `保护体系`

**现象**：一次故障现场只留下一个故障码，且它指向的是**后果**而不是**起因**。
典型：先欠压停机，随后又报堵转；先霍尔异常停机，随后又报软件过流。故障码
"总在后面变"，追不到第一原因；同一台机器不同次故障的码完全对不上物理现象。

**物理根源**：故障码通常是"第一个写入者赢"（`if(fault == 0) fault = X;`）。
物理事件有先后：起因先发生，但它的**判据节拍更慢**（电压/温度要消抖、要多次
平均；而过流/堵转在 ADC 中断里当拍就判）。于是**判据快的故障后写覆盖判据慢的
起因**，记录下来的却是后判的故障。多个判据判同一物理事件（断电、堵转伴随
零流）时会重复消耗重启额度。

**判断方法**：
1. **按"判据节拍"排时序**：把每个保护块的裁决周期列出来（ADC 当拍 / 1ms 节拍 /
   16ms 平均），快的覆盖慢的——覆盖关系由此确定，不必等复现。
2. **看写入点是否"条件写"**：搜所有 `fault =` 的赋值点，标出是否有
   `if(fault == 0)` 这类"先到先得"保护；没有保护 = 后写覆盖。
3. **交叉验证**：打印"起因物理量"（母线/温度/霍尔沿时间戳）与故障码的先后，
   若故障码总是**晚于**物理起因，即为覆盖而非误判。

**处理思路**：
- **按优先级仲裁而非先到先得**：给每个故障类配一个优先级（数值越小越优先：
  硬件短路 > 缺相/功率硬锁 > 软件过流 > 传感器类 > 可恢复类 > 自恢复类）。
  写入时"仅当本次优先级更高才覆盖"，同级/低级只执行保护动作（封波/停机）、
  **不覆盖诊断码、不重复消耗重启额度**——注意"保护动作"与"诊断码"必须分离：
  低优先级事件照样要停机，只是不许改写原因。
- **首因单独留档**：`first_fault` / `first_fault_code` 只在首次写入、**永不清零**
  （成功启动后也不清），现场复位前可追溯最初原因；与"当前故障码"分离存放。
- **子类码与主码分离**：主码表达"处置策略"（要不要重启/要不要锁死），子类码
  表达"具体触发项"；两者不要混用一个数字。

**交叉引用**：`fault-handling.md` 坑5（子类码混用导致策略错配）、坑6（只判
"是否已有故障"会吞掉同级新事件）。

## 坑2：恢复分支裸写"启动态"，把期间插入的新故障覆盖掉

**适用标签**：`状态机` `恢复放行` `竞态` `多中断源`

**现象**：故障刚恢复就又立刻停机，或"停机后莫名其妙自己转起来"；偶发，且
只在故障与恢复**挨得很近**（几百微秒~几毫秒）时出现。调阈值无用。

**物理根源**：恢复分支（"电压回来了就重新启动"）典型写法是：
`if (条件恢复) state = START;`。判据（电压、温度）与写状态之间隔着几十条
指令，这段时间里硬件级故障 ISR（短路/过流/LVD）可以插入：它置 `STOP` + 置故障码，
而恢复分支随后照旧写 `START`——**故障停机被覆盖**，机器在故障态下重新开波。
反方向也成立：恢复分支写 `START` 后，故障 ISR 才插入，机器已进入启动流程，
带着故障继续跑。

**判断方法**：
1. **把"判据 → 写状态"之间的时间窗量化**（几条指令，十几微秒级），再看这期间
   有哪些 ISR 会插入（列出全部中断源与优先级，含硬件保护）。
2. **静态审查所有写"启动态/运行态"的位置**：确认它们前面有没有"复查故障状态"
   这一步；没有复查处 = 有覆盖窗口。
3. **压力复现**：在故障恢复窗口内人为注入故障（如在恢复分支前触发一次 LVD），
   若必然出现"带故障启动"，即坐实。

**处理思路**：
- **写状态前在临界区内复查**：关中断 → 复查"故障码/子类码/锁死计数/重启挂起/
  事件序号"→ 全部仍匹配才写启动态 → 开中断。临界区只做几个字节的读写，
  几十条指令量级。
- **用"事件序号"代替"故障码"做一致性判据**：只比故障码不够——同级事件被仲裁
   拒绝时故障码不变但**确实又停了一次机**（见坑1）。给每次故障事件一个自增
   序号（停机入口自增），恢复分支记录进入时的快照，序号变了即"期间有新事件"，
   放弃放行。
- **启动事务原子化**：清故障码 + 清计数 + 迁移状态必须整体在临界区内完成；
   临界区前发生的故障由复查拦下，临界区内发生的故障在临界区出口立即响应，
   临界区后发生的故障直接覆盖状态（此后不再有写状态的点）。

**交叉引用**：`hall-sensor.md` 坑6（停转判据只看"无沿超时"、不看"已反转"，
   属同类"判据与物理状态不同步"）、坑7（方向/速度符号被吞掉反向）。

## 坑3：开波授权与故障判定非原子，故障停机后 PWM 被重新打开

**适用标签**：`PWM` `使能` `竞态` `短路保护`

**现象**：硬件短路（比较器/BKIN 封锁）明明触发了，电机却"又转起来"；或短路
停机后电机仍有极小的抖动/啸叫。误以为"短路保护没生效"。

**物理根源**：状态机里"开波"和"写运行态"是两三条指令，而**硬件故障 ISR 优先级
最高**（短路比较器），可在任何指令点插入：
```
写 CCR(占空比) → [短路ISR 插入: 清 MOE, 置 STOP, 置故障码] → 写 MOE(开波) → 写 state=RUN
```
被抢占的 case 体返回后继续执行原有的"置 MOE + 写 RUN"，把故障停机覆盖掉，
PWM 在短路状态下被重新开放——这是安全级事故（桥臂直通）。

**判断方法**：
1. **列出所有"开波点"**（写 MOE=1 / 使能输出的寄存器），逐个问"它前面有没有判
   故障、在不在临界区内"。
2. **复核中断优先级**：故障 ISR 的优先级是否高于跑状态机的那个 ISR；高于就存在
   插入窗口（无论概率多低）。
3. **看是否有"唯一的开波闸门"**：如果全工程有多处开波点、没有集中闸门，风险
   随改动线性增长。

**处理思路**：
- **把"判故障 + 置 MOE + 写状态"压成一个原子操作**：关中断 → 判无故障则置 MOE
  并迁移状态，否则强制清 MOE 回停机态 → 开中断。临界区只有一次判据 + 两个
  寄存器写（亚微秒级），不占 PWM 周期。
- **封波放在临界区之外**：硬件响应（BKIN）不等待软件互斥；软件互斥只用于共享
  状态的读改写。
- **上游状态迁移不要各自写 MOE**：宁可让上游把状态"写成脏值"，也由唯一的开波
  闸门兜底判故障并拉回停机——比在每处状态迁移加锁更不易漏。

**交叉引用**：`instrumentation.md` 坑2（高优先级中断抢占测量窗口的时间被计入）、
坑3（高优先级中断重入同一外设寄存器组覆盖运算参数）——同属"多优先级共享资源"
家族。

## 坑4：重启间隔沿用上一个故障的剩余计时，新故障的间隔被截短或拖长

**适用标签**：`重启策略` `状态机` `计时`

**现象**：两种重启间隔（如 500ms 通用 / 3s 堵转）混用时，出现"堵转故障不到
1 秒就重试"或"普通故障等了 5 秒才重试"；重启节奏不稳定。

**物理根源**：重启倒计时通常是"挂起标志为真就累加计数，到阈值清标志"。若在
等待期内又来了新故障，**挂起标志本来就已经是真**，计数不会归零，新故障直接
继承了上一个故障的剩余时间；反过来，等待期尾端来了一个需要更长间隔的新故障，
它会沿用旧故障已经计过的短间隔。

**判断方法**：
1. **列出各故障类的间隔要求**与"挂起标志"的置位/清零逻辑，检查"新故障到来时
   计数是否归零"——不归零即存在继承。
2. **构造时序推演**：故障A(长间隔) → 等待 90% → 故障B(短间隔) → 看B实际等了多久。
   与设计值不符即坐实（不必上机）。

**处理思路**：
- **给每次重启请求一个事件序号**：置挂起标志时序号自增；计时器记录"已消费的
  序号"，序号变化即把计数清零重新计——新故障从 0 开始自己的间隔。
- **间隔与故障类绑定**：按当前故障码选间隔时，注意"等待期内故障码可能被更高
  优先级改写"，选档要在计时起点取快照，或用"本次故障请求携带的间隔档位"，
  不要在到期瞬间再读全局故障码。

## 坑5：不同物理对象的故障复用同一子类码，处置策略被错配

**适用标签**：`故障编码` `处置策略` `自恢复/锁死`

**现象**：某类故障本应"锁死等断电"，实际却在不停重启；或本应"条件恢复即重启"
的故障被拖进计数锁死，多重启几次后莫名锁死。

**物理根源**：为了让"一个大类 + 若干子类"表达故障，常见做法是"一个主码（表示
处置策略）+ 若干子类码（表示具体触发项）"。**处置策略是按主码还是按子类码
决策的**，取决于实现；一旦恢复分支改成"按子类码判断是否自恢复"，而两个物理
对象完全不同的故障共用了同一个子类码，策略就错配了。典型：MCU 供电低压检测
（VDD）与母线欠压检测（VOL 母线）——前者要计数重试+锁死，后者应条件恢复即
重启；共用了"欠压"子类，恢复分支把 VDD 低压也当自恢复型 → 无额度上限、无
间隔地反复启动。

**判断方法**：
1. **列出每个子类码对应的物理对象**，问："这些对象的处置策略真的相同吗？"
   母线欠压（可自恢复）与芯片供电低压（必须锁死）就是典型反例。
2. **核对恢复分支的判据粒度**：它读的是主码、子类码，还是两者组合？
3. **看锁死载体**：没有独立锁死载体时，复用子类会直接导致"永不锁死"。

**处理思路**：
- **物理对象不同就分子类**：即使同属一个大类，不同物理对象、不同处置策略的
  故障必须占不同子类码。
- **把"处置策略"显式化**：每个故障类声明其策略（锁死 / 停机不重启 / 计数重试 /
  自恢复），由策略驱动计数、间隔与恢复路径，不靠散落在各处的隐含判断。
- **自恢复型与计数型的差别要在代码里显式区分**：自恢复型不消耗重启额度、不参与
  锁死、不等重启间隔；计数型消耗额度、超限锁死、按间隔重试。

## 坑6：仲裁只看"是否已有故障"，同级新事件被静默吞掉

**适用标签**：`诊断码` `竞态` `事件序号`

**现象**：故障码长期停在某个值不动，即使现场明明又发生了一次更严重的事件；
或恢复分支反复"看到"一个早已过期的故障状态而误放行。

**物理根源**：仲裁条件写成"已有故障则保留原码、不再处理"。但"被拒绝"的那次
事件**照样执行了保护动作（封波/停机）**——即机器又停了一次，故障码却没变。
恢复分支只看故障码/子类码，看不出"期间又停过一次"，于是把已经过期的状态
当成当前状态继续走（例如据此放行启动）。

**判断方法**：
1. **对比"事件次数"与"码变化次数"**：打印每次停机事件与故障码，若事件数多于
   码变化数，即存在被吞事件。
2. **审查恢复分支的一致性判据**：只比码 → 不足；需要能识别"码没变但状态变了"。

**处理思路**：
- **停机入口自增事件序号**：每次故障事件（无论是否改写诊断码）都自增；恢复分支
  以进入时的快照做一致性判据，序号变化即放弃放行。
- **"拒绝"也要留痕**：被仲裁拒绝的事件至少要能被观察到（事件序号、计数），
  否则现场完全看不到"发生过什么"。
